# Решения по открытым вопросам спецификации

Раздел 8 `project.md` оставлял десять вопросов. Что решено в v1 и почему.

| # | Вопрос | Решение в v1 |
|---|--------|--------------|
| 1 | Память 512 МБ на Render (free) и Playwright | Браузер **выключен по умолчанию** (`BROWSER_ENABLED=false`) и подключается двумя путями: внешний сервис по CDP (`BROWSER_WS_ENDPOINT`, рекомендуется для free-тарифа) или локальный Chromium (`--build-arg WITH_BROWSER=1`, нужно >512 МБ). Одна страница за раз, отдельный контекст без cookie, картинки/шрифты/медиа блокируются, таймауты, автозакрытие через 60 с простоя, лимит heap Chromium. Чтение действий — безопасно; клики и ввод (`browser_act`) всегда требуют подтверждения. Работу проверили на реальном Chromium (Edge) в тестах. |
| 2 | Веб-поиск через ChatGPT | **Обновлено:** используется встроенный веб-поиск ChatGPT — инструмент `web_search` Responses API передаётся модели вместе с остальными (`CHATGPT_WEB_SEARCH=true` по умолчанию), работает в рамках подписки, отдельный ключ не нужен. Свой поиск на Brave Search API убран: у него больше нет бесплатного тарифа. Если бэкенд отвергнет такой запрос, провайдер один раз повторит его без поиска и запомнит это. Вживую встроенный поиск через OAuth-вход не проверялся. |
| 3 | Эндпоинты OAuth ChatGPT | Сверено с исходниками `openai/codex`: `CLIENT_ID=app_EMoamEEZ73f0CkXaXp7hrann`, `https://auth.openai.com/oauth/authorize` и `/oauth/token`, PKCE S256, redirect `http://localhost:1455/auth/callback`, параметры `id_token_add_organizations` и `codex_cli_simplified_flow`; бэкенд `https://chatgpt.com/backend-api/codex/responses` (Responses API, SSE) с заголовками `chatgpt-account-id` (из claim `https://api.openai.com/auth` в id_token), `OpenAI-Beta: responses=experimental`, `originator`. ## Отступления и дополнения к черновику схемы данных

Таблицы из раздела 7 реализованы все. Добавлено то, без чего v1 не работает:

* `sessions` — серверные сессии (в БД хранится только SHA-256 токена);
* `notes`, `reminders`, `notifications` — заметки, напоминания и входящие уведомления;
* `usage_log` — учёт токенов и денег для бюджета;
* `oauth_flows` — временное хранение `code_verifier` PKCE;
* в `messages` — вызовы инструментов (`tool_calls`, `tool_call_id`, статус `pending` для ожидающих подтверждения);
* в `tasks` — `next_run_at`, счётчик запусков, диалог текущего запуска; статусы расширены значениями `failed` и `cancelled`;
* в `actions_log` — `undo` и `undone_at` для отката; в `approvals` — `summary` и связь с задачей/диалогом.

На всех таблицах включён RLS без политик: ключ `anon` не видит ничего, сервер ходит напрямую по `DATABASE_URL`.

## Что сознательно не входит в v1

Как и в спецификации: управление рабочим столом, коннекторы, голос, команда агентов, маркетплейс скиллов, публикация в App Store, Telegram-бот. Дополнительно:

* **Нативные push-уведомления.** На sideload-сборках iOS (бесплатный Apple ID) они технически недоступны. Вместо них: **Web Push в PWA** (iPhone с iOS 16.4+ при установке на экран «Домой», Android, десктоп) — настоящие уведомления на экран блокировки без платного аккаунта; в нативных сборках — входящие уведомления со счётчиками и баннером, пока приложение открыто.
* **Транспорт стриминга.** Не SSE/WebSocket, а быстрый опрос (~0,4 с, пока агент работает): работает одинаково на вебе и в нативных клиентах (React Native не умеет читать потоки `fetch`) и не упирается в прокси Render. Клиент сглаживает пачки текста анимацией печати.
* **Несколько пользователей.** Один пароль на инстанс; Supabase Auth — «позже», как в спецификации.

## Проактивность и надёжность данных

* **Проверки (`CheckinsService`).** По тику планировщика, не чаще `everyHours` и вне тихих часов агент запускается во временном контексте с данными (задачи, напоминания, подтверждения, прошлые свои сообщения) и узким набором чтения; ответ «НИЧЕГО» не публикуется, иначе сообщение попадает в единый разговор и уходит push-уведомлением. По умолчанию выключены — тратят токены.
* **Наблюдатели.** Отдельного механизма нет: агент создаёт периодическую задачу, а ответ «НЕТ ИЗМЕНЕНИЙ» подавляет и сообщение, и уведомление.
* **Кнопки в push.** Уведомление о подтверждении содержит действия «Одобрить/Отклонить»; service worker вызывает API с cookie сессии. На iOS кнопок в уведомлениях нет — там открывается приложение.
* **Резервная копия.** `GET /api/backup` отдаёт JSON со всеми данными (без токенов ChatGPT, сессий, ключей push — это секреты, привязанные к серверу); `POST /api/backup/restore` заменяет данные одной транзакцией и требует явного `replace: true`. Через неё делается переезд с базы Render на Supabase ([`MIGRATION.md`](MIGRATION.md)).
* **Понятные ошибки.** При сбое ChatGPT чат показывает, что делать (войти заново, лимит подписки, таймаут).

## Единый сквозной разговор и экономия токенов

Главная вкладка — один бесконечный разговор (`conversations.is_main`, он один), без списка чатов; прежние чаты доступны в «Ещё → Архив тем». Чтобы длинная лента не съедала токены, используется схема, как у компактификации в Claude Code:

1. **Сводка вместо истории.** Когда хвост разговора после последней сводки занимает >75 % окна контекста (`AGENT_CONTEXT_TOKENS`), старая часть сжимается моделью в сводку (`conversations.summary`, `summary_upto`), а недавние ~30 % окна остаются дословно. В контекст идут: системный промпт + память + сводка + хвост. Сжатие идёт в фоне после ответа; в ленте остаётся метка «ранее — в сводке памяти».
2. **Подробности по запросу.** Инструмент `history_search` ищет по полной истории, включая уже сжатые реплики.
3. **Субагент `research`.** Тяжёлый веб-поиск выполняется в отдельном временном контексте (только `read_url`/`browser_read` плюс встроенный поиск модели, до 8 шагов, до 80 тыс. токенов) и возвращает в разговор лишь выжимку; временный контекст удаляется.
4. **Прочее:** результаты старых инструментов усекаются, картинки уходят только из трёх последних сообщений, устойчивые факты агент пишет в долгосрочную память.

Клиент не тянет весь разговор: грузит последние 60 сообщений, остальное — кнопкой «Показать ранее». Утренняя сводка и итоги фоновых задач публикуются в ленту сообщением от Polaris.

## Вложения-изображения

Фото прикрепляются к сообщению (до 4 штук, до 8 МБ каждое): веб уменьшает их до 1568 px и сжимает в JPEG, телефон — через `expo-image-picker` (камера/галерея, качество 0,6). Данные хранятся в таблице `attachments` в base64 — так они переживают перезапуск на Render free, где диск временный. Модели картинки уходят как `input_image` (Responses API) только из трёх последних сообщений с вложениями, остальные заменяются пометкой «[Прикреплено изображение: …]» — чтобы не тратить токены. **Генерация изображений не реализована**: в API Codex-бэкенда ChatGPT такой возможности не подтверждено, в системном промпте агент честно об этом говорит. Приём картинок моделью через вход по OAuth в разработке вживую не проверялся.

## Дизайн клиента

Единая светлая тема: бежевая «бумага» (`#F5F0E6`), чернильный текст и основные кнопки, один терракотовый акцент. Минимализм: ответы агента без «пузырей» (с рендером Markdown и кнопкой копирования), сообщения пользователя — тёплые пилюли; тонкие границы вместо теней, тень только у поля ввода. Анимации — на встроенном `Animated` без новых зависимостей: появление элементов (`FadeIn`), нажатие (`PressScale`), три точки «думаю» с подписью текущего инструмента. Тёмной темы в v1 нет.
