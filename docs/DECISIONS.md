# Решения по открытым вопросам спецификации

Раздел 8 `project.md` оставлял десять вопросов. Что решено в v1 и почему.

| # | Вопрос | Решение в v1 |
|---|--------|--------------|
| 1 | Память 512 МБ на Render (free) и Playwright | Браузер **выключен по умолчанию** (`BROWSER_ENABLED=false`) и подключается двумя путями: внешний сервис по CDP (`BROWSER_WS_ENDPOINT`, рекомендуется для free-тарифа) или локальный Chromium (`--build-arg WITH_BROWSER=1`, нужно >512 МБ). Одна страница за раз, отдельный контекст без cookie, картинки/шрифты/медиа блокируются, таймауты, автозакрытие через 60 с простоя, лимит heap Chromium. Чтение действий — безопасно; клики и ввод (`browser_act`) всегда требуют подтверждения. Работу проверили на реальном Chromium (Edge) в тестах. |
| 2 | Веб-поиск через ChatGPT | Не используется. Поиск — собственный инструмент `web_search` (Brave Search API), он не зависит от провайдера модели. Инструмент появляется, только если задан `BRAVE_API_KEY`. |
| 3 | Эндпоинты OAuth ChatGPT | Сверено с исходниками `openai/codex`: `CLIENT_ID=app_EMoamEEZ73f0CkXaXp7hrann`, `https://auth.openai.com/oauth/authorize` и `/oauth/token`, PKCE S256, redirect `http://localhost:1455/auth/callback`, параметры `id_token_add_organizations` и `codex_cli_simplified_flow`; бэкенд `https://chatgpt.com/backend-api/codex/responses` (Responses API, SSE) с заголовками `chatgpt-account-id` (из claim `https://api.openai.com/auth` в id_token), `OpenAI-Beta: responses=experimental`, `originator`. Всё вынесено в переменные `CHATGPT_*`. **Не проверено вживую** с реальной подпиской (в разработке её не было): протокол покрыт тестами на моках; если OpenAI изменит параметры, достаточно поправить переменные окружения. Кнопка «Проверить вход» делает реальный запрос и отдельно сообщает о `model_not_found`. |
| 4 | Условия OpenAI и публичный опенсорс | OAuth-провайдер остаётся в ядре (как требует спецификация), но: **выключен по умолчанию**, включается переключателем в настройках, всегда **последний** в цепочке, в интерфейсе — явное предупреждение о личном использовании на своей подписке и неофициальности доступа. Одна подписка на инстанс, ротации аккаунтов нет. Модуль изолирован в `server/src/providers/chatgpt/` — его можно удалить одной правкой в `bootstrap.ts`. Окончательное решение о публикации — за автором репозитория. |
| 5 | Пинг Render | `pg_cron` (Supabase) раз в 10 минут дёргает `/health`, плюс раз в минуту `POST /internal/tick` (защищён `CRON_SECRET`) — он не только будит сервер, но и запускает просроченные задачи, напоминания и сводку. Готовые команды: `supabase/optional/pg_cron_jobs.sql`. Запасной план — платный Render или VPS (тот же `Dockerfile`). |
| 6 | Расписание GitHub Actions для iOS | Автоматического расписания нет: сборки iOS, Android и Windows запускаются вручную (`workflow_dispatch`), потому что macOS-минуты дороги, а переподпись раз в 7 дней всё равно делается на стороне пользователя. |
| 7 | Схема провайдеров и фолбэк | Порядок: `PROVIDER_ORDER` (по умолчанию OpenRouter → Gemini → Ollama), **ChatGPT OAuth всегда последний**. Таймаут на провайдера `PROVIDER_TIMEOUT_MS` (60 с). При 429, таймауте, 5xx, сетевой ошибке, пустом ответе и вообще любой ошибке запрос целиком уходит следующему. Провайдер после 429/сбоя получает паузу (учитывается `Retry-After`, 30 с по умолчанию, максимум 10 мин) и пробуется в конце очереди. **Частичных ответов нет**: провайдеры вызываются без стриминга, поэтому при обрыве запрос просто повторяется на следующем (поток ChatGPT при обрыве считается ошибкой). Если сбоят все — пользователь видит понятное сообщение в чате. |
| 8 | Anisette и SideStore | В репозиторий не входит: это внешняя инфраструктура. В README описаны оба пути (Sideloadly и SideStore); адрес Anisette-сервера нужно проверить на момент настройки. Резерв — PWA. |
| 9 | Имя `polaris-pl` | Проверка занятости на GitHub/npm/домене в этой среде невозможна. Пакеты помечены `private`, в npm ничего не публикуется; `bundleIdentifier` `pl.polaris.app` лёгко заменить в `client/app.json`. |
| 10 | Лицензия | MIT (`LICENSE`), как в спецификации. |

## Отступления и дополнения к черновику схемы данных

Таблицы из раздела 7 реализованы все. Добавлено то, без чего v1 не работает:

* `sessions` — серверные сессии (в БД хранится только SHA-256 токена);
* `notes`, `reminders`, `notifications` — заметки, напоминания и входящие уведомления;
* `usage_log` — учёт токенов и денег для бюджета;
* `oauth_flows` — временное хранение `code_verifier` PKCE;
* в `messages` — вызовы инструментов (`tool_calls`, `tool_call_id`, статус `pending` для ожидающих подтверждения);
* в `tasks` — `next_run_at`, счётчик запусков, диалог текущего запуска; статусы расширены значениями `failed` и `cancelled`;
* в `actions_log` — `undo` и `undone_at` для отката; в `approvals` — `summary` и связь с задачей/диалогом.

На всех таблицах включён RLS без политик: ключ `anon` не видит ничего, сервер ходит напрямую по `DATABASE_URL`.

## Что сознательно не входит в v1

Как и в спецификации: управление рабочим столом, коннекторы, голос, команда агентов, маркетплейс скиллов, публикация в App Store, Telegram-бот. Дополнительно:

* **Push-уведомления.** На sideload-сборках iOS (бесплатный Apple ID) их нет технически. Вместо них — входящие уведомления: счётчики на вкладках и баннер, пока приложение открыто. Для Android/платного аккаунта push можно добавить позже.
* **Стриминг ответов.** Клиент опрашивает сервер (раз в ~1 с, пока агент работает): это проще и надёжнее за прокси Render.
* **Несколько пользователей.** Один пароль на инстанс; Supabase Auth — «позже», как в спецификации.
